Set up 2026-08-05 at the user's request: run Alpaca paper trading as a second, parallel instance alongside the existing IBKR paper instance, to compare broker execution/fills against the identical strategy set — not to replace IBKR. See [[project_ibkr_paper_trading_setup]] for the IBKR instance's own history.

**Why parametrize-in-place instead of a separate checkout**: the host has only 2.9GB free disk (85% used, 20GB total) and `.venv` alone is 2.5GB — a second full checkout/venv genuinely didn't fit. User explicitly chose "parametrize the data paths, single checkout" over a git-worktree-with-symlinked-venv alternative.

**Architecture — one codebase, two systemd services, three new env vars**:
- `FIRM_API_PORT` (`src/firm/api/app.py`) — was hardcoded to 8000; only `FIRM_API_HOST` was configurable before.
- `FIRM_DATA_DIR` (`src/firm/api/app.py`, `src/firm/api/routers/live.py`, `src/firm/api/routers/logs.py`) — was six hardcoded `"data/..."` literals in `live.py` (`_APPROVALS_PATH`, `_TRADE_HISTORY_ORDERS_PATH`, `_TRADE_HISTORY_CYCLES_PATH`, `_KILL_SWITCH_STATE_PATH`, `_STATE_DB_PATH`, `_MEMORY_LOG_PATH`) plus the log file paths in `app.py`/`logs.py` — all now derive from this one env var (default `"data"`, unchanged behaviour when unset). `data/cache/` (market-data cache) is deliberately NOT parametrized — shared/read-mostly across both instances is fine and desirable (avoids double API cost for fundamentals).
- `FIRM_LIVE_CONFIG` already existed (added earlier) — just pointed at the new `config/live_alpaca.yaml`.
- All state-file writers (`trade_history.py`, `state_store.py`, `approval.py`, `logging_setup.py`) already `mkdir(parents=True, exist_ok=True)` their parent — no manual directory pre-creation needed; `data_alpaca/` is created automatically on first boot.

**Files**:
- `config/live_alpaca.yaml` — copy of `config/live.yaml` with `broker: "alpaca_paper"` and `danelfin_dynamic_universe.state_path` repointed at `data_alpaca/...`. Deliberately mirrors every strategy/universe/risk setting so this is a true broker-only comparison, not a confounded experiment.
- `deploy/ai-trading-alpaca.service` — same shape as `ai-trading.service` but: no `ibgateway.service` dependency/`ExecStartPre` wait (Alpaca's REST API needs no local gateway), `FIRM_API_PORT=8001`, `FIRM_DATA_DIR=data_alpaca`, `FIRM_LIVE_CONFIG=config/live_alpaca.yaml`, same `FIRM_LLM_CONFIG=config/llm_ab_quant.yaml` as production (kept identical on purpose). Same `.env` file as the IBKR instance (shared `ALPACA_API_KEY`/`ALPACA_SECRET_KEY`/`ALPACA_PAPER`, already present).
- `.gitignore` — added `data_alpaca/` (mirrors the existing per-file `data/*.json` runtime-state ignores).

**AlpacaBroker was already a complete, working implementation** (`src/firm/brokers/alpaca.py`, real `alpaca-py` SDK, every `Broker` abstract method) — zero broker-code changes needed, just the wiring above. No dedicated `tests/test_alpaca*.py` exists though (unlike IBKR) — worth adding if this instance's results start mattering for real decisions. Minor pre-existing rough edge noticed, not yet fixed: `AlpacaBroker.get_position()` treats *any* exception as "no position" (INFO-level log, not error) — could mask a real auth/API failure as "flat" during reconciliation.

**nginx/firewall**: exposed on a *separate external port* (`8443`, not a `/alpaca/` path prefix) — the shared `frontend/dist` build uses root-absolute asset paths, so a path-prefix proxy would break asset loading without a second, differently-`base`'d frontend build. `/etc/nginx/sites-available/ai-trading` now has a second `server { listen 8443 ssl; ... proxy_pass http://127.0.0.1:8001; }` block, same cert/htpasswd/rate-limit zone as the main site. `ufw allow 8443/tcp` opened to match.

**If this recurs / needs revisiting**: tomorrow's 2026-08-06 09:30 EDT cycle is the first real trading test for the Alpaca side — check `GET http://localhost:8001/api/live/cycles` the same way as the IBKR incident in [[project_ibkr_paper_trading_setup]]. Since both instances share `.venv`/`frontend/dist`/the git checkout, a `pip install`/`npm install`/frontend rebuild affects both — there's no per-instance dependency isolation.

**Same day, follow-up: user asked "why not use one service for both brokers / one frontend" — answered (every live endpoint reads a single `app.state.live_engine` singleton, no broker-id concept anywhere, so that's a much bigger refactor than scope here) and user accepted keeping the two-service split.** Then asked for "same port 443, different URL" instead of the 8443 approach — investigated and it's blocked by the frontend itself: `frontend/src/api/client.ts` hardcodes `const BASE = '/api'` (root-relative), so a `/alpaca/` nginx path prefix would still send the SPA's API calls to the domain root (port 8000/IBKR), not the intended backend — nginx-only cannot fix this without either a real second hostname (Host-header routing, zero frontend changes) or a frontend rebuild with a `/alpaca/` Vite `base`. User has IP-only access (no second hostname available), so kept the port-8443 setup as-is. **If a domain name is ever added**: hostname-based nginx routing on a single port 443 becomes clean and requires no frontend changes — revisit then.

**Same day: scoped and built two additional Alpaca services the user asked about ("can you use additional services from Alpaca?"), explicitly skipped three.**
- Research confirmed: `AlpacaBroker` (`src/firm/brokers/alpaca.py`) only ever did order execution — the Alpaca instance's strategies were still pulling prices/fundamentals/sentiment from the same generic FMP/Massive/Danelfin `FallbackProvider` as everyone else, via `build_live_providers()`'s catch-all branch (no dedicated Alpaca data source existed, unlike IBKR's own `IBKRProvider`).
- **Built**: `src/firm/data/providers/alpaca.py` (`AlpacaProvider`) — `get_prices` via `alpaca.data.historical.StockHistoricalDataClient` (`StockBarsRequest(..., adjustment="all")` for split/dividend-adjusted daily bars, mapped to `PRICE_COLS`), `get_news_sentiment` via `alpaca.data.historical.NewsClient` (Alpaca's free Benzinga-sourced News API, same `ALPACA_API_KEY`/`ALPACA_SECRET_KEY`, scored with the same `sentiment_lexicon.score_headline` IBKRProvider already uses). Everything else (`get_fundamentals`/`get_corporate_actions`/`get_universe_constituents`/`get_analyst_ratings`/`get_ai_scores`/`get_live_signals`/`get_best_stocks`) raises `NotImplementedError` — same pattern as `IBKRProvider`, vendor-agnostic sources cover those already. Unlike IBKR's persistent socket, Alpaca's SDK is stateless REST — no connection-sharing/threading concern applies here at all.
- **Wired in two places**: (1) `build_live_providers()` (`src/firm/live/provider_utils.py`) gained an `alpaca*` branch mirroring the `ibkr*` one — `AlpacaProvider` for prices, shared `FallbackProvider` for everything else. Extracted the previously-duplicated fundamentals/sentiment/estimates/ai_scores/live_signals/best_stocks wiring into a new `_attach_auxiliary_providers(providers, label)` helper shared by both branches (was ~40 lines of copy-paste risk otherwise). (2) `FallbackProvider._sentiment_chain` (`src/firm/data/providers/fallback.py`) gained `"alpaca"` as a fourth fallback (`massive → alphavantage → finnhub → alpaca`) — benefits every instance's sentiment strategy, not just Alpaca's, since it's free and uses a key already in `.env`. Also registered in `firm/data/providers/__init__.py`'s `_REGISTRY` and added `alpaca_api_key`/`alpaca_secret_key` fields to `Settings` (`src/firm/config.py`) — pydantic-settings auto-maps these to the existing `ALPACA_API_KEY`/`ALPACA_SECRET_KEY` env vars, no new config needed.
- **Explicitly skipped, with reasons** (all confirmed via direct codebase research, not assumption): corporate actions (zero consumers anywhere in strategies/backtest — would be inert), options data (no options strategy exists in this project — 16 strategies, all equity/ETF), and Alpaca's stock screener as a second universe-discovery source (the existing Danelfin-based `danelfin_dynamic_universe` mechanism is itself still `enabled: false`/explicitly unvalidated in production — adding a competing second source before the first clears its own bar would be premature). See the `danelfin_dynamic_universe` block comments in `config/live.yaml` for that mechanism's own status if revisiting.
- **Verified**: real smoke test against live Alpaca API (not mocked) — `get_prices(['AAPL','MSFT'], ...)` returned real OHLCV bars, `get_news_sentiment(...)` returned real Benzinga headlines with scores. New `tests/test_alpaca_provider.py` (7 tests, mocked SDK clients) plus `tests/test_live_provider_utils.py` updated (the old `test_build_live_providers_fallback` used `"alpaca_paper"` as its "generic/no-dedicated-provider" example — no longer valid now that Alpaca has its own branch; repointed to a synthetic `"some_future_broker"` string and added a proper `test_build_live_providers_alpaca` mirroring the IBKR one). Both `ai-trading.service` and `ai-trading-alpaca.service` restarted after (market closed, no cycle running, safe window) and confirmed picking up the new providers via their own log lines (`"Alpaca live sentiment: Massive → Alpha Vantage → Finnhub → Alpaca fallback chain"` etc.), zero errors post-restart.

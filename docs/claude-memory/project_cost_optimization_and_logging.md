**Context:** VPS is resource-constrained — **2 CPU cores, 3.3GB RAM** (confirmed via `nproc`/`free -h`), already at load average ~6 under light load. Any CPU/RAM-heavy addition (ML inference, etc.) is a real operational risk to the live trading loop (which also runs IB Gateway, a Java process) — weigh this before adding anything similar in the future.

**LLMLingua (real prompt compression) — installed, works, deliberately NOT used in the live path:**
- Installed `llmlingua` + CPU-only torch (`pip install torch --index-url https://download.pytorch.org/whl/cpu` first, ~192MB, else it pulls the ~2GB CUDA stack this machine can't even use — no GPU present). Total added ~1GB, disk had headroom.
- Real bug fixed: `PromptCompressor` defaults `device_map="cuda"` unconditionally (not auto-detected) — on CPU-only torch this makes transformers' model-loading warmup probe CUDA and raise `AssertionError`. Fixed in `TokenCompressor._get_lingua()` (`src/firm/llm/compression.py`) with `device_map = "cuda" if torch.cuda.is_available() else "cpu"`.
- **User decision after seeing a CPU spike (unrelated — was VSCode's pylint LSP re-indexing, not our code) surfaced the 2-core/3.3GB constraint:** keep LLMLingua installed and working, but **off by default** — real LLMLingua loads a ~700MB BERT model resident for the process lifetime and costs 1-2s of CPU-heavy inference per call, real contention with IB Gateway during live cycles. Gated behind `config/llm.yaml`'s `optimization.use_llmlingua` (default `false`); `TokenCompressor(use_llmlingua=True)` to opt in for offline/backtest use. Default behavior still uses the cheap sentence-sampling fallback (`_simple_truncate`).
- Also clarified for the user: LLMLingua only reduces LLM prompt tokens (helps against TPM rate caps on Groq/OpenRouter), does **not** reduce request counts (RPM — that's the model pool/fallback), and has **zero** effect on Voyage/embedding usage — compression and embedding are unrelated systems. Since Groq/OpenRouter are free-tier, there's no direct dollar saving either, just rate-cap headroom.

**Real Voyage cost drivers found and fixed (this is where the user's "6% of Voyage cap already used" actually came from — not LLMLingua):**
1. `DocumentChunker.chunk()` (`src/firm/rag/chunker.py`) let a single sentence-regex "sentence" become one oversized chunk if it exceeded `chunk_size` — HTML-extracted SEC filing text (tables, unpunctuated legal runs) produced ~1650-token chunks against a 500-token target. Fixed with a `_hard_split` fallback that windows oversized "sentences" into `chunk_size`-respecting pieces.
2. Separate bug in the same file: `chunk_by_sections`' regex alternation tried headers in listed order, not longest-match, so `"Item 1"` shadowed `"Item 1A"`/`"Item 10"`/etc. (a header that's a prefix of another). Fixed by sorting headers by descending length before building the pattern — general fix, not SEC-specific.
3. `SECIngestor` (`src/firm/rag/ingestors/sec_ingestor.py`) now filters 10-K/10-Q filings to just the high-value narrative sections (Item 1, 1A, 3, 7, 7A — business/risk/legal/MD&A/market-risk), dropping Item 8 (raw financial-statement tables, usually the largest section) and governance/exhibit boilerplate (Items 2, 4-6, 9-15). Gated on `form_type in ("10-K", "10-Q")` specifically — 8-Ks use an unrelated "Item 2.02"/"Item 9.01" event-code numbering that shares literal prefixes with several `_SECTION_HEADERS` entries, so naively section-filtering 8-Ks would misdetect them as having real Item-N structure and filter their actual (often more sentiment-relevant than 10-K boilerplate) content away to nothing. 8-Ks are now always ingested whole.
4. `VectorStore.add_documents` (`src/firm/rag/store.py`) previously had a comment claiming "ChromaDB silently skips duplicates by ID" — **false**; `upsert()` always re-embeds and overwrites. Fixed to check `collection.get(ids=...)` first and only embed genuinely new documents — makes re-running ingestion over already-stored content free (skips the Voyage call entirely) rather than silently re-paying for it. Relies on chunk ids being a content+identity hash (already fixed earlier this session).
5. `VoyageEmbeddingFunction._embed` (`src/firm/rag/voyage.py`) batched purely by count (128 texts), which — combined with bug #1 above — blew Voyage's 120K-token/request cap when SEC chunks were larger than assumed. Now token-aware via Voyage's own local `Client.tokenize()`, flushing a batch on either the count or a 100K-token safety margin.

**LLM response cache vs. load-balancing tension — fixed:** `LLMService._select_model` (`src/firm/llm/provider.py`) used to round-robin via an incrementing counter, meaning identical repeated prompts got sent to a *different* model each time and almost never hit the response cache (whose key includes the model). Fixed to route by a deterministic hash of the message content instead — same prompt always lands on the same model (cache hits work), different prompts still spread across the pool (load-balancing intent preserved). Verified live: 3 identical calls all routed to the same model, with `cache_hits=2` on repeats.

**Rotating structured logging wired up (was built but unused) — the "end-to-end logging + AI self-reflection" ask:**
- `firm/logging_setup.py`'s `setup_logging()` already existed (rotating JSON file handler, 10MB × 5 backups = 50MB ceiling per stream) but was called nowhere except `firm/scripts/fetch_data.py`. Also found `firm/scripts_entry.py` (dead code — referenced only in stale `egg-info/SOURCES.txt`, nothing real imports it) had a broken `from firm.logging_setup import configure_logging` — that function never existed. Fixed the import and wired `setup_logging()` into the real entry points: `firm.api.app:run()` (backs `firm-api`) → `data/logs/api.log`, `scripts/run_live_trading.py` → `data/logs/live_trading.log`, `scripts/run_until_profitable.py` → `data/logs/run_until_profitable.log`.
- Also fixed `setup_logging()` itself: it only configured the `"firm"` logger, so third-party libraries used throughout the live path (ib_async, litellm, chromadb) — whose loggers aren't under `"firm.*"` — were never captured, losing exactly the kind of diagnostic output that mattered tonight (ib_async's market-data-subscription warnings). Now configures the root logger instead, so everything in the process is captured. Console output stays a plain human-readable line (for watching a live session); the rotating file is JSON (for grep/jq or feeding to an LLM reflection pass later).
- **The "AI reflects back to self-improve" mechanism already exists and works**: `TradingMemoryLog` (`src/firm/agents/memory.py`, JSONL at `data/memory/decisions.jsonl`) — two-phase decision log + LLM reflection, already wired into the live engine's `_maybe_reflect`/`store_decision`. Confirmed real entries from tonight's live test runs already in that file. This is a separate mechanism from the general rotating logs above (structured decision history for LLM reflection vs. general debug/observability logs) — both now work, nothing further needed there unless the user wants them tied together.

**Why this matters:** these bugs were invisible to the existing test suite (498→573 tests over the session) because every prior test either used synthetic data or mocked providers in a way that never exercised a genuine multi-provider merge or a real rate-limit/free-tier-truncation event. They only surfaced by actually running `fetch-data` for the real 25-symbol universe and a real walk-forward backtest end to end. **How to apply:** don't trust `data_source="cache"` backtests or `fetch-data` output as correct just because the test suite is green — if touching this pipeline again, re-verify against a real fetch + backtest, not just unit tests with mocked providers.

Six bugs found and fixed in one straight-line debugging session (`src/firm/data/providers/fallback.py`, `tiingo.py`, `src/firm/scripts/fetch_data.py`, `src/firm/backtest/run.py`), each only surfacing once the previous one was fixed and the next real failure mode was exposed:

1. **`FallbackProvider._try_chain` accepted a partial multi-symbol result as fully resolved.** `MassiveProvider.get_prices()` catches errors per-symbol internally, so a rate-limit event partway through a batch returned a genuinely non-empty but partial DataFrame — accepted as "done," so Tiingo/AlphaVantage/FMP never got a chance to fill in the rest. A 25-symbol request silently cached only 5. Fixed: track per-symbol resolution, not whole-batch.
2. **`TiingoProvider` had no `__init__` accepting `settings=`** — inherited the bare `DataProvider.__init__(self, api_key)`. `_load()` always calls `get_provider(name, settings=cfg)`, and that `TypeError` wasn't in `_load`'s except clause, so it crashed the *entire* fetch (and would crash a live cycle) the moment a real rate limit forced an actual fallthrough to Tiingo. Also widened `_load`'s except clause to catch any provider-constructor exception — one broken provider must never take down the whole chain.
3. **`fetch_data.py`'s cache keys omitted the symbol list** (`f"{kind}/{provider}/{start}_{end}"`) — `ParquetCache.make_key()` already existed and included symbols (used correctly elsewhere in `scripts_entry.py`, an orphaned/unused module), `fetch_data.py` just wasn't using it. Re-running for a different universe against the same provider/date-range silently returned a stale/wrong-universe cached result.
4. **Mixed date dtypes across providers broke pyarrow on merge.** Massive/FMP/AlphaVantage store `date` as a normalized tz-naive Timestamp; Tiingo used `.dt.date` (python `date` objects) with tz-aware "Z"-suffixed source strings. Concatenating two providers' results in one merge (which only actually happens once a real rate limit forces it) crashed pyarrow's parquet writer, and even a naive dtype-normalize fix still crashed on tz-naive-vs-aware mixing (`ValueError: Tz-aware datetime cannot be converted... unless utc=True`). Fixed both the Tiingo source (parse `utc=True` then `tz_localize(None)`) and added a defensive normalization at the one merge point in `_try_chain`.
5. **Massive's free tier silently truncates history to ~2 years instead of erroring.** It returned real, non-empty data for AAPL/MSFT/NVDA/GOOG/AMZN, so the "any non-empty rows" resolution check accepted it as fully resolved and Tiingo (which had the full 6.5-year range for every *other* symbol in the same run) never got a chance. Fixed: `_try_chain` now tracks the earliest date each provider actually returned per symbol; a symbol only counts as resolved once some provider's coverage reaches near the requested start (10-day slack), and whichever provider reaches furthest back wins outright (no splicing two providers' series for one symbol). A truncated answer is kept only as a last resort if nothing fuller ever turns up.
6. **`execute_backtest()`'s real-data path (`data_source != "synthetic"`) never filtered `load_prices()`'s output by `start_date`/`end_date` at all** — `BacktestEngine`/`load_feeds` has no concept of a date range, it just runs over whatever rows are in the DataFrame. A 5-fold walk-forward run produced bit-for-bit identical metrics across every fold (each silently ran the *entire* 2020-2026 dataset regardless of its assigned window) — the synthetic branch never exposed this since `make_synthetic_prices()` is explicitly written to generate only the requested span, and the only existing `execute_backtest` test only used `data_source="synthetic"`. Fixed by filtering `prices_df` to `[start_date, end_date]` in the real-data branch.

**Known follow-up, not yet fixed:** the fix for #6 filters to exactly each fold's test window with zero lookback buffer, so strategies with long rolling-window features (e.g. a 200-day moving average) have no warmup at the very start of a fold. `ExperimentRunner.run_walk_forward` already computes `train_start`/`train_end` per fold but never uses them for anything beyond fold metadata. Wiring up a real warmup buffer (loading `[train_start, test_end]` but only scoring `[test_start, test_end]`) is a larger design change than this bug fix and is worth doing before trusting walk-forward Sharpe/drawdown numbers on strategies with long lookbacks.

**Verified final result:** after all six fixes, `fetch-data` for the real 25-symbol universe (2020-01-01 to 2026-07-20) gave every symbol identical, complete coverage (1,644 rows, 2020-01-02 to 2026-07-20 — confirmed via direct cache inspection, not just the CLI's summary line). A 5-fold walk-forward backtest across all 12 strategies then produced genuinely different, plausible per-fold metrics (e.g. Sharpe -0.38 in the 2022 bear-market fold vs. +3.66 in the most recent fold; mean Sharpe ~1.0, mean CAGR ~7%, mean hit rate ~52%).

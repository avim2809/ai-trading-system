A "deep audit of the past week" request turned up two critical, silent live-trading outages, both root-caused and fixed same session (1417 tests green), deployed by restarting `ai-trading.service` + `ai-trading-alpaca.service`.

**1. IBKR: zero orders submitted for 5+ consecutive trading days (Aug 10-14).** Root cause: `ibgateway.service` auto-restarts nightly (~02:45 IDT, systemd-scheduled, confirmed via journalctl restart counter incrementing daily), but `firm-api`'s `IBKRBroker` connection was never proactively refreshed — the next day's market-open cycle discovered the resulting half-open socket only after burning a 20s timeout per symbol across the whole universe (`socket.send() raised exception` → every `qualifyContracts` call times out). The existing reactive reconnect (`_try_broker_reconnect`) only fixed the *next* cycle, a full day later, and the gateway restarted again that night — same failure, every day. Fix: added `Broker.health_check()` (base default delegates to `is_connected()`; `IBKRBroker` overrides with a real `reqCurrentTime()` round-trip since `is_connected()` alone reports stale-but-locally-true) and `LiveTradingEngine._ensure_broker_healthy()`, called as the very first thing in `_run_cycle_work` (before `data_feed.refresh()`) — catches and repairs a stale connection in one fast call instead of losing the whole cycle. See [[project_ibkr_paper_trading_setup]] for the earlier (8/5) two-connections bug this is a *different* regression from — that fix (shared connection) is still correct and unrelated.

**2. Alpaca: most orders rejected since Aug 12-14** with error `40310000` "insufficient qty available" (e.g. long 3 shares, target -4 → engine submits `sell qty=7`; Alpaca allows selling down to 0 but rejects the extra 4 that would open a short in the *same* order). Confirmed via live read-only Alpaca account check this was NOT a permissions gap (shorting_enabled=True, margin 4x, real shorts already held) — it's that Alpaca requires a position-flip to be two sequential orders (flatten, then open), never one crossing zero. Fix: `AlpacaBroker.submit_order` now detects a flip via `get_position` and splits into a flatten leg + an open leg, waiting (bounded, 8s) for the flatten to actually fill before submitting the open leg (both legs are the same side, so submitting too early re-triggers the identical rejection). Deprecated flip attempts also explained the "Cash mismatch"/"Position mismatch" reconciliation noise seen those days — expected to drop now.

**3. Also fixed same session:** `gemini/gemini-2.5-pro` (the LLM reflection fallback chain's primary model) had been silently 404ing ("no longer available to new users") since ~Aug 11 — same decommissioning `gemini-2.5-flash` hit earlier (8/5). Replaced with `gemini/gemini-2.0-flash` in `src/firm/llm/providers.py` and all `config/llm*.yaml` files. Also deleted a stray untracked `MagicMock/get_settings().data.cache_dir/...` directory at repo root (454 empty dirs from an incompletely-mocked test, ~1.8M, zero real files — safe, git never saw it).

**Discord alert overhaul** (user asked mid-session, unprompted by the audit): `src/firm/live/notifications.py` previously sent a single plain-text line to Discord (`[SEVERITY] raw_snake_case_kind: message`). Rewrote it to send a proper Discord embed alongside — color-coded by severity (red/gold/blue), a human-readable title per alert kind (`_ALERT_TITLES` dict, e.g. "Kill Switch Tripped — Drawdown Breach" instead of `drawdown_breach`), and the alert's extra context (drawdown %, symbol, consecutive_failures, etc.) rendered as readable fields instead of a raw dict dump. Falls back gracefully for any future/unknown alert kind (title-cased rendering). If new alert kinds are added to `LiveTradingEngine._emit_alert` later, consider adding a friendly title/labels for them in `notifications.py`'s `_ALERT_TITLES`/`_CONTEXT_LABELS` dicts (not required — they degrade fine without it).

**How to apply:** if a future audit finds either account looking "idle" (flat equity, zero submitted orders across cycles) or "leaky" (many rejected orders), check the new `Proactive broker health check failed` / `Proactive reconnect succeeded` log lines (IBKR) or `Flip ... flatten leg` / `Flip ... open leg` lines (Alpaca) first — these are the specific signals the two fixes above emit, before assuming a new regression.

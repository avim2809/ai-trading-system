Goal: run this repo's `firm` system in automated paper-trading mode against IB Gateway with all 12 registered strategies active simultaneously (momentum, trend, mean_reversion, stat_arb, multi_factor, sentiment, event_driven, ml_prediction, volatility_breakout, seasonality, gann, regime_hmm). `config/live.yaml` encodes this as the "1_week_all_strategies_paper" experiment with a tuned, realistic risk envelope (window 2026-07-17 to 2026-07-24).

**Why:** validate strategies under live-equivalent constraints on paper before risking real capital.

**Status as of 2026-07-18: full end-to-end pipeline verified working** — IB Gateway connected via IBC headless auto-login, a real live cycle ran all 12 strategies + LLM-enhanced bull/bear/debate agents, and (after two bugs found by this test were fixed) generated and auto-submitted real paper orders with zero failures. Re-verify the checklist below before trusting it blindly on a future session — this is infra/environment state, not code, and a process restart or fresh `.venv` can silently revert parts of it.

**How to run it end-to-end:**
```
./scripts/start_ibgateway.sh paper   # headless IBC auto-login, ~15-20s to log in
set -a && source .env && set +a
.venv/bin/python scripts/run_live_trading.py --config config/live.yaml --max-cycles 1 --approval-mode auto
```
`--config config/live.yaml` (added 2026-07-18) makes the script load the real strategies/universe/risk envelope instead of just its CLI-flag defaults — see "gap" note below for why this matters.

**Four real bugs found by running the pipeline end-to-end (all fixed 2026-07-18):**
1. `IBKRBroker` (`src/firm/brokers/ibkr.py`) never called `ib.reqMarketDataType(...)`, so it defaulted to live/real-time data (type 1). Without a real-time subscription (true for this paper account and most accounts), `reqTickers` silently returns `NaN` for every field instead of erroring — the engine logged `"No price for X – skipping order"` for every symbol and generated zero orders. Fixed by defaulting to `market_data_type=3` (delayed) in the constructor, calling `reqMarketDataType` in `connect()`.
2. `LiveTradingEngine._split_by_approval` only recognises the literal strings `"full_auto"` / `"semi_auto"` — anything else (including plain `"auto"`) silently falls through to "queue everything for manual approval," with no error. Both `scripts/run_live_trading.py --approval-mode auto` **and** `AUTOMATED_TRADING_GUIDE.md`'s own curl example used the wrong value `"auto"`, so following the guide literally means orders silently never auto-submit. Fixed: the script now maps its friendly `auto` CLI choice to the engine's `full_auto` internally; the guide's curl example and `config/live.yaml`'s `approval_mode` were corrected to `full_auto` directly. The guide's curl example also referenced a fictional `"strategies": {enabled/auto_approve/require_approval}` request body key that `StartRequest` doesn't have (silently ignored) — replaced with the real `auto_approve_strategies`/`symbols` fields.
3. Fresh IB Gateway installs default their API to **Read-Only mode** (order placement blocked) until `ReadOnlyApi=no` is set. `/root/.ibc/config.ini` never had this key, so all 20 auto-submitted orders came back `Error 321: "The API interface is currently in Read-Only mode"` — real rejections, not fills. Fixed by adding `ReadOnlyApi=no` to `/root/.ibc/config.ini` (IBC's own config, not TWS/Gateway's GUI checkbox — this is the setting meant for exactly this headless/unattended case) and restarting Gateway.
4. Masked bug #3 for a while: `IBKRBroker._map_trade` (`src/firm/brokers/ibkr.py`) mapped *any* unrecognised `orderStatus.status` to `"pending"` by default. `ib_async` sets status to the non-native value `"ValidationError"` when the API rejects an order outright (e.g. the Read-Only case above), so every rejected order was reported as merely "pending" — indistinguishable from a healthy in-flight order. Fixed: `"ValidationError"` now maps explicitly to `"rejected"`, and the fallback default for any *other* unrecognised status was changed from `"pending"` to `"rejected"` (fail-safe: an unknown status must never be silently treated as still in flight).

Verified after all four fixes: a real test order via `IBKRBroker.submit_order()` was accepted cleanly (no ValidationError) and a subsequent `cancel_order()` correctly reported status `"cancelled"`. Today (2026-07-18) is a Saturday — markets closed, so no fill was expected or seen; that's independent of the Read-Only fix (IBKR accepts/queues market orders outside trading hours, it just wasn't accepting *any* order before the fix).

**Remaining known gap:** `/live/start` (`src/firm/api/routers/live.py`) still does not read `config/live.yaml` — it only accepts the fields in its `StartRequest` model. Fixed 2026-07-18 to at least default-populate `agent_modes`/`llm_config` from `config/llm.yaml` when starting (previously every analyst silently stayed in "quant" mode via this endpoint, so the LLM layer never activated for an API-started run — same fix applied to `scripts/run_live_trading.py`). **LLM layer:** Groq (`llama-3.3-70b-versatile`/`llama-3.1-8b-instant`) + several OpenRouter free models are configured with round-robin load-balancing and automatic fallback (`config/llm.yaml`, `src/firm/llm/provider.py`). Verified live during the end-to-end run: requests visibly rotated across both providers, and a real 429 on `openrouter/google/gemma-4-31b-it:free` was caught with an automatic fallback to Groq — no crash. `.env` now has real `GROQ_API_KEY` and `OPENROUTER_API_KEY` values (user added both, no longer placeholders). `OPENAI_API_KEY`/`ANTHROPIC_API_KEY` remain placeholders — not needed given the above.

**Other:** FMP's fundamentals endpoint (`/stable/income-statement`) returns HTTP 402 (plan doesn't include it) for several symbols including ETFs (QQQ, IWM, SPY — which don't have income statements anyway). Caught and logged per-symbol, doesn't crash the run, but the `multi_factor` strategy's fundamental signals are degraded for those names on the current FMP plan.

**Two more real bugs found chasing "zero orders generated" on that first full cycle:**
1. `IBKRBroker.get_current_price(s)` (`src/firm/brokers/ibkr.py`) fell back to `ticker.last` whenever `midpoint()` was NaN — but outside trading hours `last` defaults to the real float `0.0` (not NaN), so the NaN-only check silently accepted it as a genuine price. Wiring this in immediately surfaced a **third** bug already latent in `IBKRBroker.is_market_open()`: it compared IBKR's trading-hours string (expressed in the contract's own exchange timezone — `US/Eastern` for SPY) directly against `datetime.utcnow()` with **no timezone conversion**, and used `tradingHours` (extended 4am-8pm ET session) instead of `liquidHours` (regular 9:30am-4pm ET session). Because `LiveTradingEngine.run_cycle()` is serialised via APScheduler's max-instances=1 + a `threading.Lock`, that one stuck cycle blocked **every** subsequent cycle — including the *entire* 2026-07-21 trading day's scheduled run. **Worse: this is exactly the failure mode the existing `cycle_watchdog_seconds` timer (added [[project_ibkr_paper_trading_setup]]'s earlier "34-hour silent hang" fix) was built to alert on — and it never fired.** Zero `cycle_watchdog_timeout` alert, zero log line, zero traceback anywhere in that ~30 hour window, despite the default 1800s (30 min) threshold. The exact reason that `threading.Timer` callback went silent is **still unexplained** — would need live reproduction (e.g. deliberately hanging a cycle and observing in real time) to root-cause definitively; a plausible but unverified hypothesis is Python's process-wide logging lock getting stuck mid-write at the exact moment of the hang, which would silently block *any* thread's subsequent `log.critical(...)` call, including the watchdog's.

**If a scheduled cycle appears to be silently not running again**: check `/api/live/status`'s new `cycle_running_seconds` field first (or `sudo journalctl -u ai-trading.service | grep "already in progress"`) before assuming the strategies chose not to trade — a stuck cycle from a *previous* day can silently block an entire subsequent trading day with no error and no alert.

**Same day, user asked to keep debugging until the watchdog's silence itself was explained — fully root-caused (`d31f1d7`), not left as a mystery.**

1. **Why the watchdog alert never fired, historically**: deployment timing, not a code bug. `git log -S "cycle_watchdog_seconds"` shows that feature was committed (`ffbce5e`) at 2026-07-21 19:48:07 UTC — over 30 hours *after* the hung cycle started (2026-07-20 13:35:00 UTC) and only minutes before the service got restarted. The stuck process (PID 382580) had been running since 2026-07-20 07:02 UTC on code from before the watchdog existed at all — it couldn't alert using code that hadn't been written yet. Lesson: correlate `git log` timestamps against process-start/incident timestamps before concluding a fix "should have" caught something — a running process only has the code it was started with.
2. **What actually made the cycle hang in the first place — a real, separate, still-live bug, reproduced directly against the paper connection**: `is_market_open()` (`src/firm/brokers/ibkr.py`) called `ib.qualifyContracts()`/`ib.reqContractDetails()` — both blocking async round-trips tied to whichever asyncio event loop is current on the *calling thread* (`ib_async`'s `getLoop()` is thread-local). Scheduled cycles run on APScheduler's own worker thread, never the thread that called `connect()` — so this gets a brand-new, disconnected event loop with nothing registered to ever resolve the Future it awaits. Confirmed by direct reproduction: connect on the main thread, call `is_market_open()` from a second thread → hangs forever, no timeout, no error. Same class of bug `get_account()` was already fixed for ([[project_ibkr_paper_trading_setup]]'s earlier entries) — `is_market_open()` (added later, for the market-hours gate) was never given the equivalent fix.
3. **Fix**: same pattern as `get_account()` — `connect()` now fetches the SPY contract's trading-hours details once, on the connecting thread, and `is_market_open()` reads that cache (no live round-trip, ever). Added a staleness guard too: if the cached schedule has no entry at all for today (distinct from an explicit `CLOSED` holiday entry — that's a stale cache, not a holiday), fail open with a warning rather than silently reporting "closed" forever.
4. Verified against the real IBKR paper connection both ways: reproduced the hang on the pre-fix code (worker thread never returns within 20s), then confirmed the fix resolves it (~3ms from a worker thread). 21 tests in `tests/test_ibkr_broker.py`, full suite 582 passed.

**If `is_market_open()`-style code is touched again**: any *new* blocking `ib_async` call (not a plain cached read like `positions()`/`accountSummary()`) must either be fetched once in `connect()` and cached, or explicitly proven safe to call from an arbitrary thread — this whole incident happened because that check wasn't applied consistently to every IBKR call added after the original `get_account()` fix.

**2026-08-03/04: single-cycle-per-day scheduling gaps closed, then a live incident on the very first exercise of the new retry path — `qualifyContracts()` hung forever and froze the whole broker layer (`26609cf`).**

- User asked why no orders ran despite market being open: root cause was `schedule: market_open` meaning **one cycle per day** — that day's only cycle got fully blocked by a news-guard blackout (broad macro event → every order held), and with no retry logic, the rest of the trading day (6+ market hours) was silently lost. Same gap existed for a cycle that simply errored out (broker disconnect, hard timeout).
- Fixed generally in `src/firm/live/scheduler.py`: `cycle_had_no_trading_outcome(summary)` (true for "fully news-guard-blocked" OR "errored", false for any `skipped` cycle — market-closed/shutdown/concurrent-run are momentary, not lost days) + `maybe_retry_lost_cycle(engine)`, polled every 30 min via a new `lost_cycle_retry` APScheduler job (only added for session-anchored schedules). Also added `LiveTradingEngine.cycles_today()`/`reconcile_order_history()` (new `src/firm/live/order_reconciliation.py` + `TradeHistoryStore.update_order_status()`) since orders were only ever recorded once at submission and froze at "pending" forever if they filled/cancelled asynchronously — reconciliation now polls the broker every 15 min. `had_cycle_today()` also now consults persisted history (not just in-memory), closing a duplicate-cycle-on-restart risk.
- **The retry mechanism fired for the first time ever that same night and immediately hit a real, previously-dormant production bug**: the retry cycle correctly got past the (now-expired) news-guard blackout, cleared risk checks, then `submit_order()`'s `ib.qualifyContracts()` call hung indefinitely — confirmed via `py-spy dump --pid <pid>` (installed at `.venv/bin/py-spy`, very useful for this — showed the exact frame: `qualifyContracts (ibkr.py:198)` blocked inside `select()`/`asyncio`). No response ever arrived; best (unproven) theory is it landed in a ~19-minute-earlier window where IB Gateway's own log (`/root/.ibc/logs/ibgateway.log`) showed a "Connecting to server..." event (Gateway reconnecting to IBKR's own backend, not a process restart — the `java` PID had been running continuously for 22h). Since `_ib_lock` (serialising all `IBKRBroker` calls) had no acquire-timeout, that one hung call froze `get_positions`/`get_account`/reconciliation/all future cycles for the rest of the process's life — confirmed via `ss -tnp` showing huge unread `Recv-Q` backlogs on both broker connections. Only a full `systemctl restart` (needed the full 120s `TimeoutStopSec` since the stuck thread wouldn't respond to graceful shutdown) cleared it. No orders were ever submitted — the hang happened before the first one went out, so nothing was left stranded/untracked at IBKR.
- **Fix**: `ib.RequestTimeout` (ib_async's own per-request bound, defaults to `0` = wait forever — was never set) is now set to 20s in `connect()`. New `IBKRBroker._locked()` context manager bounds `_ib_lock` acquisition itself to 45s (independent second layer) and translates any `TimeoutError` into `BrokerError`, so a caller that can't get in fails fast and loud instead of hanging forever. All 8 `with self._ib_lock:` sites converted. Regression tests reproduce the exact incident (one thread holding the lock while a second waits). Verified live: clean restart, broker reconnected, positions responded instantly, zero errors.
- **Lesson**: this confirms/extends the 2026-07-21 lesson above — but this time the risk wasn't "wrong thread, no cached loop," it was "no timeout at all, on a call that inherently can't be cached (`submit_order`)." Any future *new* blocking `ib_async` call added to this file should get an explicit timeout story (either inherits `RequestTimeout` via `IB._run()`, or is proven bounded some other way) — don't assume the existing `_ib_lock` alone is sufficient defense; it only serialises, it doesn't bound.

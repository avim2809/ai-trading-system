The RAG stack (`src/firm/rag/`) is meant to ground three LLM-enhanced roles — sentiment analyst, bull researcher, bear researcher — in actually-retrieved documents (news/filings/research) before calling the LLM, instead of the LLM answering from training knowledge alone. `config/llm.yaml`'s `rag:`/`assistant:` sections configure it; embeddings/reranking default to hosted Voyage (`voyage-finance-2` / `rerank-2.5`) rather than local torch models.

**Why this matters:** sentiment/bull/bear researcher code (`src/firm/agents/llm/{sentiment,bull_researcher,bear_researcher}_llm.py`) all gate the LLM call itself on retrieval succeeding — `if not rag_context: skip the LLM, use quant only`. So if RAG is silently broken or empty, those three roles are pure-quant despite being configured `llm_enhanced`, with zero visible error. Only the debate/synthesis agent doesn't gate on RAG (calls the LLM unconditionally, RAG is bonus context if present).

**Status as of 2026-07-18: fixed and verified working end-to-end** (real Voyage embed → Chroma store → point-in-time filtered retrieval → Voyage rerank, using the user's real `VOYAGE_API_KEY`). Two real bugs were found and fixed — both were silently swallowed by `LLMAgentMixin._retrieve_context`'s broad `except Exception: return ""`, so retrieval had been returning nothing for every single call up to this point, with no visible error anywhere:

1. **Point-in-time date filter crashed every asof-filtered query.** `firm/rag/dates.py` deliberately stores document dates as lexicographically-sortable ISO strings (`"YYYY-MM-DD"`) for point-in-time correctness — a sound design. But `VectorStore.query()` (`src/firm/rag/store.py`) pushed that string into Chroma's `where={"date": {"$lte": ...}}` filter, and Chroma's `$lte`/`$gte` only accept **numeric** operands — every call raised `ValueError`. Since every real agent call passes `asof=ctx.now`, retrieval had *never* actually worked, store empty or not. Fixed: `query()` no longer pushes the date bound into Chroma's `where` clause; it over-fetches the dense-similarity candidates (whole collection, when `asof` is set) and applies the `date <= asof` cutoff as a plain Python string comparison before truncating to `n_results`. A now-dead `_and_filters` helper (only ever used to build the broken clause) was removed, along with the two unit tests that specifically validated that broken clause-shape as "correct" — replaced with a regression test (`tests/test_rag.py::TestStoreDateFilter`) using a fake Chroma collection that actually exercises `VectorStore.query()`'s real date-filtering behavior, so this class of bug (tested the plumbing, never the real dependency's validation rules) can't silently recur.
2. **`VoyageEmbeddingFunction` had no `embed_query` method.** This installed Chroma version (1.5.9) calls `embedding_function.embed_query(input=...)` for query-time embedding, separately from `__call__` for document-time embedding (some models, Voyage included, benefit from asymmetric embedding). `VoyageEmbeddingFunction` (`src/firm/rag/voyage.py`) only had `__call__`, so every query raised `AttributeError`. Fixed properly rather than just aliasing: `__call__` now passes Voyage's `input_type="document"`, and the new `embed_query()` passes `input_type="query"` — this is Voyage's own recommended pattern for retrieval quality (query vs. document embeddings differ), not just a crash fix.

Full test suite (478 tests) passes after both fixes — no regressions.

**Three more real bugs found running the actual ingestion pass (all fixed 2026-07-18), on top of the two retrieval bugs above:**
3. **`SECIngestor._fetch_filings` used field names that don't exist in the real API response** (`src/firm/rag/ingestors/sec_ingestor.py`) — `source.get("file_url", "")` and `source.get("form_type", "")`. The actual SEC full-text-search hit has no `file_url`/`form_type` fields at all; every hit was silently skipped (`if not filing_url: continue`), so SEC ingestion had *always* returned 0 documents, for any symbol, ever. Fixed: build the real document URL from the hit's top-level `_id` (`"<accession>:<primary-filename>"`) + `_source.ciks`, per SEC EDGAR's standard `Archives/edgar/data/{cik}/{accession-nodash}/{filename}` layout; use `source.get("form", "")` (the real field) instead of `form_type`. Verified against a live fetch before/after.
4. **`DocumentChunker._make_chunk` hashed only chunk *text* for the doc id** (`src/firm/rag/chunker.py`), not any document identity. Two different source documents (different SEC filing, different symbol's news) can produce byte-identical chunk text (boilerplate legal sections, syndicated wire copy, repeated risk-factor language) — hashing text alone caused a `ChromaDB DuplicateIDError` crash within a single SEC-filing ingestion batch, and silently overwrote unrelated documents across separate batches (same id → upsert just replaces). This explained an earlier "1200 chunks reported ingested, only 1004 in the store" discrepancy for news. Fixed: the hash now also incorporates `source`/`symbol`/`date`/`url` + chunk index, staying stable/idempotent for re-ingesting the *same* document while no longer colliding across genuinely different ones.
5. **`VoyageEmbeddingFunction._embed` batched purely by count** (128 texts/request) with a comment noting the ~500-token/chunk assumption might not hold — it didn't: SEC filing chunks (HTML-to-text extraction produces long run-on "sentences" with few recognized boundaries) averaged ~1650 tokens each, so a 128-text batch hit 211K tokens against Voyage's 120K/request cap (`voyageai.error.InvalidRequestError`). Fixed: batching is now token-aware, using Voyage's own local (no network call) `Client.tokenize()` to measure each text and flush a batch when either the count (128) or a token budget (100K, safety margin under 120K) would be exceeded.

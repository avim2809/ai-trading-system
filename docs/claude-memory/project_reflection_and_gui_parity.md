Two related fixes done in the same session, both stemming from the user asking "does live auto-trade perform reflection and backtests?" then "what's missing for 1:1 GUI/backend parity?":

**1. Reflection restart-safety** (`src/firm/agents/memory.py`, `src/firm/live/engine.py`, `src/firm/backtest/firm_strategy.py`): `TradingMemoryLog.store_decision()` now persists `nav_at_decision` to disk; `find_all_pending()` reads outstanding decisions back from the log instead of relying on an in-memory pointer that a process restart would silently wipe. `_get_llm_service()` failures now log a warning instead of silent debug.

**2. GUI/backend parity audit found the Configuration page was almost entirely non-functional**: frontend sent a nested payload (`strategies{enabled,auto_approve}`, `risk{...}`, `universe{symbols}`) but backend's `PUT /live/config` only read flat fields and had no `risk` field at all — saving config silently did nothing beyond `approval_mode`. Separately, `/live/start` always ran ALL registered strategies regardless of the Strategies panel, and `/live/status`'s `active_strategies` actually returned the SYMBOL universe, not strategy names (copy-paste bug). Also found `getLLMProviders()` expected a bare array but backend returns `{"providers": [...]}` — would have thrown at runtime.

**Why this matters:** confirmed with the user this was a live-trading safety issue (risk limits/strategy selection believed to be applied via GUI were not) before doing the larger fix — see [[user_profile]] pattern of "flag safety-relevant scope growth before continuing, don't just silently expand."

**How to apply:** `LiveTradingEngine` now has real `update_strategies()`/`update_risk()` methods and enforces `max_daily_trades`/`max_daily_turnover` (previously fake/decorative config, forces cycle's orders to manual approval on breach rather than blocking outright). `ConfigUpdateRequest` in `src/firm/api/routers/live.py` now mirrors `GET /live/config`'s shape exactly for round-trip symmetry. New `GET /api/memory/decisions` endpoint + `/decisions` frontend page expose the reflection log that previously had zero API surface. New `GET /live/alerts` surfaced in a LiveDashboard banner. If touching live-trading config again, verify round-trip via `TestLiveConfigRoundTrip` in `tests/test_api.py` — this whole area had zero test coverage before this session, which is exactly how these bugs went unnoticed.

Committed and pushed alongside the earlier exception-logging audit work — see [[project_exception_logging_audit]] and [[project_frontend_log_monitor]] for prior related work this session.

**2026-08-03: backtest-registry/decision-log architecture clarified; two more strategy-attribution traceability gaps found + fixed (`7d19459`).**

- User asked "is my backtest history correct?" then "how are backtests used today — are they even a signal?" — **architecture, confirmed by grep, not derivable from a quick glance**: backtests are a promotion *gate* only (evidence for whether to enable a strategy in `config/live.yaml`); nothing in `src/firm/live/` ever reads `runs/registry.json` or any backtest `report.json`. `LiveTradingEngine` computes signals independently every cycle. The dashboard's run registry (`firm.experiments.registry`, backs `runs/registry.json`) is **only populated via `POST /api/runs`** — standalone `scripts/calibrate_*.py` scripts call `firm.backtest.run.execute_backtest()` directly with zero `RunRegistry` references, so their results never appear in the Dashboard. This is why the registry can look "stale" even when calibration work is actively happening — check for recent `scripts/calibrate_*.py` runs/output before assuming the dashboard's staleness means no work happened.
- Same session, user asked why the decision log was also stale: root cause was the **same test-contamination bug already fixed once before** (missing `memory_log_path` in test configs, see [[project_ibkr_paper_trading_setup]]'s 2026-07-21 entry) having a second-order, permanent-data-loss effect — `TradingMemoryLog`'s `_idempotency_check(date)` is "one entry per calendar date, first writer wins," so a contaminated test entry landing first on a given date silently and permanently blocked that day's *real* decision from ever being recorded. Confirmed via `GET /api/live/cycles` showing real orders on dates with zero decision-log entries at all. **Not recoverable** — disclosed this honestly rather than attempting a heuristic backfill.
- **Two independent instances of the same "strategy attribution silently dropped before persistence" bug**, both fixed: (1) Order History showed no originating strategy — `OrderRequest.strategy` was set correctly at submission but discarded because `OrderStatus` (broker-level type) has no strategy field and `_status_to_dict()` never re-attached it; fixed by threading `(OrderStatus, strategy)` pairs through both `_execute_orders` (auto-submit) and `ApprovalQueue.approve()` (manual-approval) call sites. (2) Decision log's reflection prompt never saw `TradeProposal.per_strategy` (genuinely computed by `TraderAgent._attribute_to_strategies()`) — the reflection LLM could only judge "the portfolio" as a whole, never name which strategy's call was right/wrong; fixed by passing `per_strategy` into `store_decision()` and including it in `reflect()`'s prompt. **User's framing, worth remembering**: "traceability is vital for reflection and lessons learned" — when investigating any reflection/decision-log/attribution issue, check whether per-strategy data is actually reaching the LLM prompt, not just whether it's computed somewhere upstream.
- Considered and rejected backfilling 84 historical orders' missing strategy from `PerformanceAttribution._trade_log` — that log's fill dicts have no `order_id`/timestamp to uniquely join against `order_history.json` rows; a heuristic symbol+side+quantity match risked misattributing strategy to the wrong order, judged worse than leaving them honestly blank.

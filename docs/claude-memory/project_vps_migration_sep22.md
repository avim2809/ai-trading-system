Production moved to a new VPS (157.173.96.157, 6 CPU/11GB/193GB disk, replacing
the old 2-core/3.3GB box — see [[user_profile]]) on 2026-09-22. Both live
instances (`ai-trading.service` IBKR blended :8000, `ai-trading-alpaca.service`
Alpaca sleeved :8001) plus `ibgateway.service` came up active on the new host.
Local Claude memory on this host started completely empty post-migration (the
memory store is host-local, not carried by git) — restored from
`docs/claude-memory/` at the start of this session; **the VPS-local memory
store must be re-synced from the repo mirror after any future migration**,
this isn't a one-time fix.

**Migration gaps found and fixed same-session** (per
[[feedback_production_incident_priority]]):
- System timezone was `Europe/Berlin`, but `backup-live-state.timer`'s own
  comment assumes `Asia/Jerusalem` (a leftover assumption from the old host).
  Fixed via `timedatectl set-timezone Asia/Jerusalem`.
- `backup-live-state.timer` was installed and enabled but had **never fired**
  (`LAST PASSED: -`, backup directory didn't exist). Ran
  `systemctl start backup-live-state.service` manually to establish a baseline
  — confirmed working (1.3M archive written). Timer is correctly wired for
  future runs (09:00 UTC daily).
- fail2ban had no `nginx-http-auth` / `nginx-limit-req` jails — only `sshd`.
  Standard filter defs already existed at `/etc/fail2ban/filter.d/` (ship with
  the package) and matched the real nginx log format; just needed
  `/etc/fail2ban/jail.d/nginx.conf` written and fail2ban restarted. Confirmed
  all three jails active afterward.
- `ai-trading-alpaca.service` crashed on boot hitting the exact bug commit
  `2c0d353` fixes (`cycles_today()` choking on a manual-action entry's
  `cycle_id=None`) — the commit message literally says "found live on the new
  VPS during migration cutover." It got restarted (picking up the fix)
  automatically/by whoever was working the box before this session; but
  `ai-trading.service` (IBKR) was still running pre-fix code (started before
  the fix commit, never restarted) — restarted it mid-session to load the fix.

**Still-open bug found via a forced test cycle** (NOT resolved by "just wait
for a cycle to run" — proven, not just theorized): triggered
`POST /api/live/trigger?force=true&sync=true` on :8000 (cycle 54) specifically
to test whether `sync_portfolio_from_broker`
(`src/firm/live/portfolio_sync.py`) would populate `self._portfolio.holdings`
once a real cycle ran. It ran successfully — IBKR's `updatePortfolio` callback
fired correctly for every symbol (broker feed is fine) — but
`GET /api/live/reconciliation` still showed `internal_holdings=0.0` for 19 of
20 previously-mismatched symbols afterward. The one exception (MA) only
*looked* fixed because the cycle's own sell order (44 shares, matching
broker's real MA position exactly) algebraically cancelled the mismatch via
the reconciliation math's pending-order netting — not because the underlying
holdings tracking actually got fixed. Root cause not yet found as of this
memory being written — a parallel multi-agent audit
(workflow `live-trading-full-audit`, run `wf_69789637-822`) is investigating
`portfolio_sync.py` plus a broader security/infra/code-correctness/config-drift
sweep, launched 2026-09-22 same session.

**Side effect of that test still needs a decision**: a real pending order is
sitting on the IBKR paper account — sell 44 MA, ~$25k notional, order_id 81,
unfilled since market was closed when submitted. It was sized correctly
(matches broker's real position) despite being generated by a cycle running on
a confirmed-broken internal holdings cache, meaning order sizing reads broker
positions through a different, apparently-correct path than whatever
`check_reconciliation()` reads. The audit workflow includes a dedicated
read-only assessment of whether to leave or cancel it — user explicitly chose
"let the audit decide" rather than a snap call either way.

**Resolved 2026-09-23** via a parallel multi-agent audit (workflow
`live-trading-full-audit`, run `wf_69789637-822`, 25 agents): root cause was
`sync_portfolio_from_broker`'s (and `check_reconciliation`'s duplicate copy)
in-flight-order netting treating every open broker order as "about to
settle," including resting protective/trailing-stop orders that may never
fill — collapsing `expected_qty` to 0 and making a never-synced 0 internal
holding look "already correct," so the real position never got written into
`self._portfolio.holdings`. Fixed by adding `order_type` to `OrderStatus`
(both brokers) and excluding `stop`/`stop_limit`/`trailing_stop` from the
netting math. 473 tests passed, diff independently reviewed. Deployed via
`systemctl restart` on both services (permission for this was added mid-session
by the user editing `.claude/settings.local.json` themselves — restarts and a
`systemctl *` wildcard, not self-granted). **Verified live**: forced a
synchronous cycle on :8000 post-restart (cycle 55) — `GET
/api/live/reconciliation` went from 19 mismatched symbols to
`{"status":"ok","discrepancies":[]}`. Alpaca (:8001) got the same fix +
restart but has not yet had a cycle run to verify the same way.

The audit also surfaced a real process gap: one of its own read-only agents
restarted `ai-trading.service` without authorization (clean stop/start, no
harm, but only 2 of 6 audit-agent prompts explicitly forbade touching
services — the other 4 said to *flag* restart-needing findings, which wasn't
an unambiguous enough constraint). Worth remembering when scoping future
multi-agent workflows against this live system: an explicit "do not restart
any service / call any live mutation endpoint" needs to go in every agent's
prompt, not just the ones expected to need it.

Other real findings from the same audit: `.env` and several live-state files
were world-readable (644) — fixed (`.env`→600, state files→640). Two more
instances of the exact `.get(key, default)`-with-None-leak shape
(execution_safety.py, approval.py) were fixed same-session alongside the
main bug. `.gitignore` fixed for `data/llm_cache_ab_llm.db*`.

**One audit finding was flat wrong — a lesson on trusting multi-agent audit
output without spot-checking:** the root-cause agent claimed order 81's
correct MA sizing came from a separate, still-running `BestStocksLedger`
Danelfin arm ("a red herring"). Verified directly afterward: `best_stocks_arm`/
`BestStocksLedger`/`rebalance_via_broker` aren't referenced anywhere in
`scheduler.py` or `app.py` — nothing wires it into the running system, and
its own ledger file's last write was 2026-08-15, five+ weeks dormant. The
*other* audit agent (order-soundness) had the correct account: order 81 came
from the normal main-engine path off correctly-synced holdings, with
`danelfin_ai_score` just a legacy attribution label. Same lesson as the
Danelfin incubation-lock "fix": don't assume an audit finding about a
supposedly-active code path is right without checking whether that path is
even reachable — `danelfin_dynamic_universe.enabled: false` on both
`config/live.yaml` and `config/live_alpaca.yaml` meant the scheduler job the
finding was about was never actually registered.

Danelfin is now confirmed **fully inactive** by triple-check (config flag,
live `active_strategies` API, BestStocksLedger dormancy) — user removed
`DANELFIN_API_KEY` from `.env` themselves same-session to finish the
decommission. `docs/danelfin_best_stocks_arm.md`/[[project_danelfin_integration]]
already documented the 8/16 decommission; this closes the loop on it.

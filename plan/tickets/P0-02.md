# P0-02 — Discovery freeze and forward-data seal (LIVE-IMPORT-PATH)

**Phase:** P0 **Status:** DONE 2026-10-04 (branch p0/P0-02; code merged to p0/foundation only, NOT deployed: LIVE-IMPORT-PATH window and controlled restart still owner actions; MODIFIED_SCOPE, source ticket P0-02) **Depends on:** P0-01, P0-06 **Touches live services:** yes (LIVE-IMPORT-PATH, behaviour-neutral by design) **Owner decisions:** OD-04, OD-05, OD-07

## Rationale (cite source plan / literature)
Source P0-02: "Discovery freeze and holdout seal. The 2024-07->2026-06 holdout is burned (hold-out reuse unreliable) ... seal_date = 2026-10-01; data after = forward holdout, never available to research code until human-run unseal, used once per family ... PointInTimeDataStore gets hard max_research_date = seal_date; raises unless HOLDOUT_UNSEAL_TOKEN (human-held)." Literature: Bailey, Borwein, Lopez de Prado & Zhu (2017): a standard hold-out reused many times is "unreliable and inaccurate"; Harvey, Liu & Zhu (2016) on multiple testing. Source A11/Caveats: instructions are advisory, enforcement must be technical, and "Physically keeping holdout off the agent machine is the only fully reliable control" (GitHub issues #24846, #61208).

## Repo reconciliation (what exists today, exact paths+line refs, what changes vs source plan and why)
1. There is no historical holdout and never was. The only repo-defined "holdout" is a Gann backtest window 2024-07-01..2026-06-30 (`scripts/gann_followup_study.py:62-63` on origin/research/gann-archive). The whole 2020-01-01..2026-06-30 cache panel was reused by about 28 later evaluations, and the EODHD studies read data through 2026-09-28/30. Decision (OD-04): everything up to 2026-09-30 is declared in-sample and burned; `seal_date = 2026-10-01`; only data from 2026-10-01 on is sealed.
2. The source interface `PointInTimeDataStore.get(symbol, start, end, asof)` does not exist. The real class is `src/firm/data/pit_store.py:18` with `get_prices(symbols, asof, lookback_days)` (L92), `get_fundamentals` (L118), `get_estimates` (L153), `get_ai_scores` (L175), `get_market_percentile_pool(asof, lookback_days)` (L220; takes `asof`, called by the live adapter at `src/firm/live/data_feed.py:163`), `get_sentiment` (L248), `load_macro`/`get_macro` (L266/L280), `get_universe(asof)` (L307), `get_universe_union(start, end)` (L327), and `load(...)` (L44). `get_live_signals` (L197) and `get_best_stocks` (L211) take no `asof`; they are covered only through `check_frame` on `load()`. The seal check is on `asof` (and on `end` for the union).
3. A guard confined to the store would be bypassed by research code that reads parquet directly (`scripts/run_*_evaluation.py`, `scripts/eodhd_clean.py clean_bars`). Therefore the plan has a second chokepoint, `firm.research.data_access`, which all new harnesses must use. Existing frozen scripts are not changed.
4. Post-seal data already sits on this host and the live services keep writing it: `data/cache` (refreshed by live services), `data/` and `data_alpaca/` (both FIRM_DATA_DIRs), `data/research/s2_forward/` (frozen S2 shadow job), `docs/s2_forward_snapshot.json` (tracked), `logs`, and later `data/forward_monitors/` and `research/monitoring_sealed/`. The seal on this host is therefore enforced by ACL (OD-07: separate non-root research user without read access to those paths) plus deny rules plus a fail-closed loader. It is not physical absence. HOLDOUT_POLICY.md states this.
5. LIVE-IMPORT-PATH. `pit_store.py` is used by the live engine: `src/firm/live/data_feed.py:29,92-152` calls `get_prices`, `get_fundamentals`, `get_sentiment`, `get_estimates`, `get_ai_scores` with `asof` equal to the current live time, which is after the seal. `runtime.py` is imported at module top by `src/firm/live/engine.py:42`, and the live fundamentals path (`data_feed` -> `fundamentals_cache` -> `runtime.load_fundamentals`, `runtime.py:212`) swallows errors at debug level. A guard that raised in the live process would silently drop live fundamentals. So the hook is default-None and only `firm.research.seal` installs it; live modules never import `firm.research`.
6. Source test "request past seal raises; without token env var ignored" is kept, with a changed meaning: the token check is not in code that live paths run. The token preimage is held by the owner; config stores its sha256 only.
7. DoD item "holdout dir absent from agent working tree" cannot be met by code alone (no `data/holdout/` exists; data sits in `data/research/eodhd` 4.7 GB and `data/cache`). It becomes: the research user has no read access to the post-seal locations, and `data/holdout/` is gitignored (P0-06).

## Algorithm notes / pseudocode (keep the source plan's formulas exactly where they apply; correct them explicitly if wrong, with reason)
```python
# seal.py
def check_asof(asof, what):
    d = pd.Timestamp(asof).date()
    if d > max_research_date():            # max_research_date() = burned_through = last usable day
        raise HoldoutAccessError(f"{what}: asof {d} > max_research_date {max_research_date()} (seal_date {seal_date()})")
# RECONCILED: the source says 'raises if end > max_research_date'. This ticket keeps that exact form by defining
# max_research_date() as the last usable day (burned_through), which equals seal_date minus one day, so callers cannot
# make an off-by-one error by comparing against the first sealed day.
# data_access.load_panel: fail closed unconditionally.
#   - end must be < seal_date, else raise.
#   - allow-list first: a path must resolve under one of allow_roots, else raise. Everything else under data/ is refused, including the
#     IBKR FIRM_DATA_DIR contents (data/live_state.db, data/logs, data/cycle_history.json, ...), which hold post-seal prices, NAV and fills.
#   - then any path under deny_paths -> raise (no env var, no heuristic, no 'if not in research mode').
#   - after loading, check_frame(df) as a second line.
```
- No environment-variable detection and no heuristic ("is this a research process?") anywhere. Research entry points call `seal.install_guards()` explicitly (via `data_access` first use and later `backtest_logged`, P1-01).
- Guard semantics inside `pit_store`: getters check `asof`; `load(...)` and `load_macro` check the frames they receive with `check_frame`. A research backtest therefore must pass pre-sliced frames from `data_access`; passing the live `data/cache` panel after it has been refreshed past the seal raises (fail closed, by design).
- Residual risk, stated in HOLDOUT_POLICY.md and recorded under OD-04: the guard is fail-open for any code that never imports `firm.research`. It is mitigated by the research-user ACL (P0-04/OD-07) and by P1-12, which marks such runs non-promotable.
- Human knowledge of post-seal market moves cannot be avoided. HOLDOUT_POLICY.md requires every core_v1 choice to be frozen and dated in its prereg before P3-08 with a declaration that no post-seal data was examined.
- Unseal: once per family, no earlier than 12 months of accrued data (P3-10, earliest 2027-10-01). The unseal script is owner-run; this ticket only reserves the `unseal_log` structure.

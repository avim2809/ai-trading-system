# P3-07 — Named stress suite

**Phase:** P3 **Status:** DONE (batch8/stress; owner actions pending) **Depends on:** P3-09, P0-02 **Touches live services:** no **Owner decisions:** none

## Rationale (cite source plan / literature)
Source plan P3-07 and G-RESEARCH 5 (B2): no named episode may lose more than 1.5x the charter's pre-committed max drawdown, every episode is reported, and the suite is never used to tune. Trend systems are exposed to sharp reversals (the last three episodes are trend-hostile), and named windows make the report auditable by a third party.

- RECONCILED: **Seal.** The source says "periods after the seal are evaluated only during human unseal". With `seal_date = 2026-10-01` (OD-04), all ten named periods end by 2025-05-31 and are pre-seal, and therefore (like all data to 2026-09-30) in-sample and already burned. The suite is therefore a reporting device, not an out-of-sample test. The report says so.
- **Instrument availability.** Many ETFs have inceptions in 2002-2007, and the vol warm-up (P3-01) needs 256 return days before an instrument enters (and 2520 days for the full long-run window, with the expanding fallback). In the GFC window some instruments are not yet active, so each episode reports the number of active instruments and which they are. This is a required output column (design: G-RESEARCH 5).
- RECONCILED: **Threshold reference.** Episode loss vs `1.5 * charter max-DD`, where the charter max-DD is the pre-committed bootstrap p95 procedure on the selected config at 1x cost, evaluated at each episode's own length (P5-02 `max_dd_procedure`, OD-16 split rule). It is never the resettable live peak. The suite takes the reference as an input (a number, or a function of episode length).
- Real data is read only in P3-08 via `firm.research.data_access`. Here the suite is a pure function over a returns frame plus positions, tested on synthetic data.

## Algorithm notes / pseudocode (keep the source plan's formulas exactly where they apply; correct them explicitly if wrong, with reason)
Named periods, exactly as in the source (inclusive dates), stored in `config/stress_periods.yaml`:
1. GFC 2008-09-01 to 2009-03-31
2. Flash crash / euro 2010-04-15 to 2010-07-15
3. US downgrade 2011-07-15 to 2011-10-15
4. Volmageddon 2018-01-26 to 2018-04-30
5. Q4 2018 2018-10-01 to 2018-12-31
6. COVID 2020-02-15 to 2020-04-30
7. 2022 inflation 2022-01-01 to 2022-10-31
8. Regional banks 2023-03-01 to 2023-03-31
9. Yen-carry 2024-07-15 to 2024-08-31
10. Liberation Day 2025-03-15 to 2025-05-31
The last three are trend-hostile reversals (source).

Per episode: slice returns, then `total_return = prod(1+r)-1`; `max_drawdown` = largest peak-to-trough loss of the episode equity curve starting at 1.0 at the episode start (so it is not path-dependent on earlier equity); `worst_day = min(r)`; `realised_vol = std(r, ddof=1)*sqrt(256)` (same annualisation as P3-01); `vol_ratio = realised/target`. `breach = max_drawdown > 1.5 * reference_max_dd`.

Clarifications:
- RECONCILED: episodes with fewer than `min_days` observations are reported with `n_days` and `status='unusable'` rather than silently dropped or scored. An episode with zero active instruments is `not_applicable`, and one whose active-instrument fraction is below the pre-registered `min_active_fraction` is `low_coverage`. All are visible rows and are counted in `suite_summary`. Downstream, P3-08 treats any non-`ok` episode as gate 5 `insufficient` (Tier C), never `pass`, so warm-up or universe choices cannot silently remove the GFC or another key episode.
- Active instrument count comes from `positions` (non-NaN history, an instrument is active on the date once it has passed the warm-up gate). If `positions` is None, the field is -1.
- Reporting only: the module has no optimiser, no parameter search and no dependence on tuning parameters. Any parameter change after viewing a result is a new trial and a new prereg (source rule).
- `reference_max_dd` is a required argument with no default. A test enforces it.

## Tests & acceptance criteria (concrete test file names and assertions)
`tests/test_stress_suite.py` (synthetic only):
- `test_config_has_ten_periods_exact_dates`: parses `config/stress_periods.yaml` and compares all ten names and dates against literals in the test (the test fails if anyone edits the file, in addition to the hash check in the prereg).
- `test_all_periods_before_seal`: every `end` is before the `seal_date` read from `config/research_freeze.yaml` (P0-02).
- `test_hand_computed_episode`: a 5-day return fixture gives a hand-computed total return, max DD and worst day to 1e-12.
- `test_drawdown_starts_at_episode_start`: a prior large loss before the window does not enter the episode max DD.
- `test_breach_flag_at_1p5x`: a max DD of exactly 1.5x the reference is not a breach, and 1.5x plus epsilon is.
- `test_active_instruments_counted`: a frame in which two instruments start mid-window reports 1 then 2 active (a GFC-like fixture).
- `test_short_window_reported_not_dropped`.
- `test_unusable_and_low_coverage_counted`: `suite_summary` reports `n_unusable` and `n_low_coverage` and `all_ok=False` for a fixture with a short window and one with coverage below the threshold.
- `test_reference_required`: calling without `reference_max_dd` raises `TypeError`.
- `test_no_tuning_api`: no function in the module accepts a callable or parameter grid (`inspect` check on public functions).
- `test_import_light` (subprocess): no `firm.live`, `firm.api`, `firm.runtime`. P0-06's isolation test passes.

**Phase:** P4 **Status:** DONE (batch11/risk2; draft config, OD-16 register rows pending) -- was EXTEND_EXISTING (source ticket P4-04) **Depends on:** P4-03, P5-02, P1-10, P2-03 **Touches live services:** no **Owner decisions:** OD-16

## Rationale (cite source plan / literature)
Source P4-04: soft WARNING at 1.0x and hard kill at 1.5x of the charter maximum drawdown, or operational faults (stale data over 2 days, broker disconnect in the rebalance window, position break), each fault-injection tested. The source also notes little evidence that DD de-risking adds return, so soft is alert-only here. Source A9: the analytic drawdown bound 2.5 tau. Design (OD-16 split rule): the charter max-DD is already a procedure in source P5-02 (95th percentile of a bootstrapped drawdown distribution) (stationary block bootstrap, Politis-White block length, seed, 10,000 draws, selected config at 1x cost). For kill-switch and decommission survival thresholds use `max(bootstrap p95, 2.5 tau)` so a lucky backtest cannot set a hair-trigger; G-RESEARCH 5 uses the stricter bootstrap p95.

```python
# src/firm/risk/kill_switch.py
class Tier(str, Enum):
    OK = "ok"; SOFT = "soft"; HALT = "halt"; HARD = "hard"
    # SOFT: alert only. HALT: operational fault, block new orders. HARD: DD >= hard_mult*survival_ref, block new orders.

class Action(str, Enum):
    NONE = "none"; BLOCK_NEW_ORDERS = "block_new_orders"; FLATTEN = "flatten"
    # FLATTEN is never emitted by default; it needs an owner-signed OD-16 rule and is forbidden while stale_data or broker_disconnect is active.

@dataclass(frozen=True)
class KillSwitchConfig:
    charter_dd_bootstrap_p95: float      # from the ledger-derived artefact, not risk.yaml
    tau: float
    soft_mult: float = 1.0
    hard_mult: float = 1.5
    stale_data_days: int = 2             # trading days
    # no soft_exposure_factor: soft is alert-only (source). Adding de-risking needs an OD-16 row
    # and a key in the P5-02 charter front matter + tests/integrity/test_charters.py first.

    @property
    def survival_ref(self) -> float:     # max(p95, 2.5 * tau)
        return max(self.charter_dd_bootstrap_p95, 2.5 * self.tau)

@dataclass(frozen=True)
class KillSwitchState:
    hwm: float                           # immutable high-water mark of the unit-value series (measurement, decommission)
    hwm_date: date
    halted: bool
    tier: Tier
    resume_baseline: float | None        # approval-set re-arm point (unit value); None before any reset
    resume_hwm: float | None             # running max since resume_baseline
    resets: tuple[dict, ...]             # audit records, append-only
    nav_corrections: tuple[dict, ...]    # audited exclusions of bad observations, append-only

@dataclass(frozen=True)
class Decision:
    tier: Tier
    action: Action
    triggers: tuple[str, ...]            # "dd_soft", "dd_hard", "stale_data:SPY", "broker_disconnect", "position_break"
    exposure_factor: float               # 1.0 always, except 0.0 under an owner-signed FLATTEN
    already_halted: bool                 # engine_halted or breaker_active
    dd_immutable: float                  # vs immutable HWM (feeds decommission, P5-01/P6-01)
    dd_from_baseline: float              # vs resume_hwm if a reset exists, else equals dd_immutable (drives the tier)
    alerts: tuple[dict, ...]             # emitted only on a tier transition
    state: KillSwitchState

def unit_value(returns: pd.Series) -> pd.Series: ...      # cash-flow-adjusted (time-weighted) series from daily returns
def drawdown(unit_values: pd.Series, hwm: float) -> float: ...
def evaluate(unit_values: pd.Series, state: KillSwitchState, cfg: KillSwitchConfig, *,
             last_bar_date: Mapping[str, date], today: date, broker_connected: bool,
             in_rebalance_window: bool, position_breaks: Sequence[Mapping],
             engine_halted: bool = False, breaker_active: bool = False) -> Decision: ...
def record_reset(state: KillSwitchState, *, approver: str, reason: str, at: datetime,
                 current_unit_value: float) -> KillSwitchState: ...
def record_nav_correction(state: KillSwitchState, *, bad_date: date, approver: str, reason: str,
                          at: datetime) -> KillSwitchState: ...
```

## Algorithm notes / pseudocode (keep the source plan's formulas exactly where they apply; correct them explicitly if wrong, with reason)
- Input is a cash-flow-adjusted unit-value (time-weighted) series built from returns, NOT raw NAV: P7-02 adds capital in steps (25% -> 50% -> 100%), so a deposit must not inflate the HWM and a withdrawal must not create drawdown.
- `hwm = max(state.hwm, max(unit_values))` (never decreases, excluding dates in `nav_corrections`); `dd_immutable = (hwm - u) / hwm`.
- Tier drawdown measure: `dd_from_baseline = (resume_hwm - u) / resume_hwm` once a reset exists (resume_hwm = running max since `resume_baseline`), else `dd_immutable`.
- `soft` if `dd >= soft_mult * survival_ref` (alert only, `Action.NONE`, `exposure_factor` 1.0). `hard` if `dd >= hard_mult * survival_ref` -> `Action.BLOCK_NEW_ORDERS` (matches the engine's existing halt; it does not liquidate).
- Operational (source: hard-kill triggers, meaning stop trading): `stale_data` if any held instrument's last bar is older than `stale_data_days` trading days; `broker_disconnect` if `in_rebalance_window and not broker_connected`; `position_break` if any discrepancy. Any of these gives `Tier.HALT`, `Action.BLOCK_NEW_ORDERS`, no liquidation. FLATTEN is forbidden while stale_data or broker_disconnect is active.
- Precedence: HARD > HALT (operational) > SOFT > OK. `engine_halted` / `breaker_active` are recorded in triggers and `already_halted`, never lower the tier. Across mechanisms (P6-01/P6-03): this tiered switch acts first; the engine's legacy `allocation.kill_switch_drawdown` halt (resettable peak, `engine.py` L1316) is only a last-resort backstop, set at 1.5 x `survival_ref` on candidate instances so it cannot fire at the SOFT level; `RiskAgent._drawdown_breaker` is pipeline-only and does not apply to allocation-mode candidates.
- Reset: `record_reset` requires approver and reason, appends an audit record, leaves `hwm` untouched, and sets `resume_baseline = resume_hwm = current_unit_value`. The tier is then measured from the baseline, so an evaluate at an unchanged NAV does not re-halt, while `dd_immutable` keeps reporting cumulative loss to the decommission combiner. A further loss of `hard_mult * survival_ref` from the baseline re-triggers.
- NAV correction: `record_nav_correction` appends an audited exclusion for a bad observation date (never deletes the data); excluded dates are skipped in HWM and drawdown.
- Alerts only on tier transitions (a persistent HARD state alerts once; escalations always alert).
- Corrections vs source, each needing an OD-16 register row (cross-file): (1) the survival reference is `max(bootstrap p95, 2.5 tau)` instead of the bare charter max-DD (the source charter max-DD is already the bootstrap p95; the change is the 2.5 tau floor); (2) the baseline/re-arm mechanism after an approved reset and the NAV-correction path; (3) HARD/HALT block new orders rather than flatten. Soft semantics and operational-fault semantics are NOT deviations: they follow the source.

# P5-02 — Charter template and core charters (approved before any real-data P3 work)

**Phase:** P5 **Status:** NEW (source ticket P5-02) **Depends on:** P0-04, P1-10 **Touches live services:** no **Owner decisions:** OD-01, OD-17, OD-06 (approval identity), consumes OD-16 split rule (one bootstrap procedure, `max_dd_procedure`, serves both references: the episode-length p95 for the stress gate and `max(p95 at 2520 days, 2.5 tau)` for survival)

## Rationale (cite source plan / literature)
Source P5-02: every strategy family gets a written charter before any real-data work: mechanism, expected Sharpe with a haircut, max drawdown, decommission rules. Literature behind the haircut and the procedure: McLean & Pontiff (JF 2016) post-publication decay; Harvey, Liu & Zhu (2016) multiple-testing haircuts; Bailey & Lopez de Prado (2014) DSR; Politis & Romano (1994) stationary bootstrap and Politis & White (2004) block length; Carver, *Systematic Trading* (2015) on vol targeting. Note on 2.5 tau: it is a rule of thumb taken from the source B0 range (20-35% DD at 12-15% vol), not an analytic bound; source A9 gives DD >= 20% at 15-20% vol, about 1-1.3 tau.

The point of a charter is to commit to procedures before results exist, so a lucky backtest cannot set the kill thresholds afterwards.

## Repo reconciliation (what exists today, exact paths+line refs, what changes vs source plan and why)
- No charter concept exists in the repo. `research/` does not exist yet. The closest analogues are the frozen `scripts/*_preregistered*.py` modules (frozen constants plus `bars_fingerprint()`, e.g. `scripts/allocation_forward_test_preregistered.py:259`) and docs such as `docs/allocation_forward_test_plan.md`. - Kill-switch regimes today are bare config numbers: IBKR 8% (`config/live.yaml`, `kill_switch_drawdown`), Alpaca 25% (`config/live_alpaca.yaml`). They are not tied to any charter. This ticket does not change them.
- Differences from the source plan:
  1. Charters pre-commit procedures, not numbers that only exist after a backtest. The max-DD entry is a procedure: stationary block bootstrap, Politis-White block length, recorded seed, 10,000 draws, 95th percentile, applied to the selected config's 1x-cost backtest. The result is stored in the ledger as a derived artefact, not typed into the charter by hand.
  2. Split rule (OD-16): G-RESEARCH 5 uses the bootstrap p95 (stricter). Kill-switch and decommission survival thresholds use `max(bootstrap p95, 2.5 tau)`, so a lucky backtest cannot create a hair-trigger. The analytic 2.5 tau (source A9) is always reported alongside.
  3. tau (target vol) is set ex ante from long-run asset vols without performance input (OD-17); about 8-10% is expected on the ETF path (long/flat, gross <= 1.0x, half the universe bonds). The charter also fixes the "fraction of days at the gross cap" ceiling of 20%; exceeding it is a G-RESEARCH 6 failure.
  4. The mechanism section is human-written and committed before the first ledger trial of the family. CI (P0-04 integrity job) checks git timestamp ordering: charter commit earlier than first ledger row for the family. Timestamps come from `git log`/`date -u`, never log lines (host clock is Asia/Jerusalem).
  5. Carry charter only if OD-01 selects the futures path. Default scope is ETF trend (EWMAC), ETF breakout, and the combined core.
  6. Expected-Sharpe haircut of at least 50% is stated, and gate-7(b) correlation-<=0.3 diversification rationale is written in `core_combined.md` if branch (b) is to be used.

## Algorithm notes / pseudocode (keep the source plan formulas exactly where they apply; correct them explicitly if wrong, with reason)
Template sections, in order: (1) Mechanism (human-written; economic reason the premium should exist, who is on the other side, why it should persist). (1b) Evidence base (citations). (2) Universe and instruments (link to P2-01 files); rebalance frequency, expected turnover and annual cost in bps. (3) Expected Sharpe: published or pre-seal-independent prior, minus haircut >= 50%; expected worst year and longest flat period. (4) tau and derivation. (5) Max-DD procedure and split rule, formulas. `path_length_days` is the bootstrapped path length: the max-DD distribution grows with path length, so it is fixed ex ante (default: the full research-window length, which is what the source's "backtest DD" implies; rationale recorded) and applies to both the episode test (G-RESEARCH 5) and the survival reference (the same p95, per OD-16):
- 2.5 tau rule of thumb (source B0 range; NOT an analytic bound), reported only as a companion;
- `survival_dd = max(bootstrap_p95_dd, 2.5 * tau)`; `stress_dd = bootstrap_p95_dd`; G-RESEARCH 5 limit = 1.5 x `stress_dd`; hard decommission DD = 1.5 x `survival_dd`.
(6) Decommission rules (one trigger -> PROBATION and review; two -> weight 0 automatically and approval to resume; matches G-DECOMMISSION in gates.yaml). (7) Correlation expectations and diversification rationale (correlation <= 0.3 branch of G-RESEARCH 7, if used). (7b) Falsification (its own section). (8) Declarations: no post-seal data examined; core_v1 choices frozen before P3-08. (9) Approval block.

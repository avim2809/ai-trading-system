## Rationale (cite source plan / literature)
Source P5-04 wants a fidelity monitor (live vs shadow replay). The repo already has a frozen forward-test pre-registration whose implementation bars are computed by nothing: `grep` shows `simulated_nav` and `tracking_error` only inside `scripts/allocation_forward_test_preregistered.py`. Every day without the monitor means I1/I2 can only be reconstructed later (acceptable, since replay is deterministic from stored closes, but it should start now). This ticket is also the first real dataset for the P5-04 tooling. Literature: implementation-shortfall framing of Perold (1988); tracking-error as the standard fidelity metric.

## Algorithm notes / pseudocode (keep the source plan formulas exactly where they apply; correct them explicitly if wrong, with reason)
```
hist = json.load(docs/allocation_forward_test_trial_history.json)   # read-only
start = hist.entries[-allocation].start_date ; expected_fp = entry.fingerprint ; initial_nav per the initial_nav decision above
cfg = yaml.safe_load(config/live_alpaca.yaml)["allocation"]
check bars_fingerprint() == expected_fp ; check cfg against PORTFOLIO (I5)
with _data_end_override(as_of_last_close):      # in-process only; restored in finally; recorded in state
    sim = replay(cfg, data_dir=<state>/inputs, start, as_of_last_close, initial_nav)
live_nav = last snapshot per US trading day at or after 16:00 ET (GET-only client), else day flagged
te_t = r_live_t - r_sim_t
I1: over rolling 63 trading days: |mean(te)| <= 5e-4 and std(te) <= 15e-4 (bps/day), excluding logged corporate-action/outage days (listed in output, never silently dropped)
I2: at each month-end |live/sim - 1| <= 0.02
I3/I4/I5/BAR_SLEEVE_DRIFT as in BARS_IMPLEMENTATION text, exactly
any_fail -> notify(severity="critical", kind="allocation_forward_bar_fail", ...) ; NO order/config action
```
Corrections: none to the frozen bar formulas; the DATA_END override, input refresh and live_nav selection rule above are operational additions, not changes to any frozen bar.

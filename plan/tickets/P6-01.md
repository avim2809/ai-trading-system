## Algorithm notes / pseudocode (keep the source plan's formulas exactly where they apply; correct them explicitly if wrong, with reason)
- Target weights: from P3-06 sizing, weights = clip(position_value / NAV), long/flat, sum <= 1.
- Buffer / execution-semantics consistency (REQUIRED, corrected from the earlier "buffer is applied in P3-06 only"): `Sleeve.target_weights(asof, history)` receives no holdings (sleeves.py L55-61), so the Carver buffer (trade only when outside [N-B, N+B], to the nearest edge) cannot be computed there, while `Allocator.plan` adds its own rules (NAV-level drift trigger `band_abs` 0.02, optional `band_within`, `cash_buffer`, `min_order_notional` 100, trading to the full target; allocator.py L306-330, build_allocator defaults ~L465-470). Choose one: (a) CarverSleeve applies the buffer against its own persisted last-executed position state, reconciled to broker holdings at each review, with the candidate config setting `drift_check=False`, `band_within=None`, `cash_buffer=0` and `min_order_notional` equal to the value P3-09 models; or (b) the P5-04 shadow replay drives `Allocator.plan` itself over the vector-engine targets. State in the PR whether P3-08's turnover/cost results were produced under the same execution semantics; if not, re-run them under these semantics before P6-02 starts. Otherwise a G-PAPER 2 failure would come from plumbing, not the strategy.
- Limit at mid: `limit = round(mid, tick)` where mid comes from the quote (or existing mid under option (b)). Escalation runs where stated below; the escalated order is a marketable limit at the touch plus a pre-set cap in bps (option (a)) or mid +/- cap (option (b)); if no usable quote, fall back to market and log WARNING.
- Escalation scheduling: the engine acts only on scheduled legs (`hourly_market_hours`: 09:30 open, 10:30-14:30 intraday, 15:50 close; scheduler.py L49-54), and `_allocation_should_run` returns False while today's orders are still working or a retry is pending and caps re-plans at `max_attempts_per_day` (3) (engine.py ~L2859-2893). Therefore `_escalate_stale_limits` runs either as a dedicated APScheduler job registered only when `execution.limit_at_mid.enabled`, or at the next scheduled leg, with `timeout` expressed in legs in that case. Escalation is part of the same attempt: it is neither blocked by the `_check_allocation_orders() == 'pending'` gate nor counted in `day_attempts`.
- Escalation safety: (1) cancel; (2) poll until the broker reports a terminal status (canceled, filled or partially filled); (3) resubmit only `target_qty - filled_qty`; (4) persist the attempt counter in engine state so a restart resumes rather than re-sending attempt 1. The attempt-suffixed `client_order_id` does not give cross-attempt broker dedupe, so steps (2)-(4) are what prevents double trades.
- Idempotency: reuse the existing day key and `client_order_id`; a re-run on the same day plans zero new orders.
- Kill-switch precedence: the tiered switch (immutable HWM, P4-04) takes precedence; the engine's legacy `kill_switch_drawdown` halt (engine.py L1316, resettable peak) is a looser last-resort backstop (candidate config sets it at 1.5x survival_ref, see P6-03). `RiskAgent._drawdown_breaker` (pipeline only) is not used in allocation mode. A 1.2x drawdown triggers the soft tier only and does not halt the engine.
